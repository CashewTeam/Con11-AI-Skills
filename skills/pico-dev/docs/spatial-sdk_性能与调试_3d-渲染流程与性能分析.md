空间应用是在 [PICO OS 6](/document/discover/pico-os-6-overview/) 上运行的一种全新应用形态。本文介绍其在统一渲染（Unified Rendering）框架下的核心渲染流程，并结合该框架的特点，提供性能分析与优化的建议。
PICO OS 6 的统一渲染流程包含两大核心角色：

* **PICO 空间引擎（PICO Spatial Engine）**：为所有空间应用提供统一渲染服务。它负责处理并合成来自多个应用的内容，最终将渲染结果提交给合成器。
* **合成器（Compositor）**：与 V-Sync (垂直同步) 信号对齐，负责将内容最终显示在屏幕上。它和 PICO 空间引擎共同构成了空间应用的渲染底层。

## 帧生命周期
PICO 空间引擎旨在通过封装标准化的渲染能力来降低开发门槛，使开发者能更专注于业务逻辑与交互体验的创新。尽管如此，为保障应用的流畅运行，你在构建渲染任务时，仍需充分考虑系统资源的合理分配，避免因单帧任务过于复杂而影响整体性能。
理解空间应用单帧画面的生命周期，有助于你更高效地利用统一渲染能力，并在出现性能问题时快速定位。空间应用一帧的生命周期分为以下四个阶段：

1. **渲染任务的创建与提交：**
   此阶段在你的空间应用进程中发生。应用根据交互输入和业务逻辑更新，创建并提交当帧的渲染任务。这些渲染任务具体指 ECS 架构中所有与渲染相关的组件（EC）数据，如 `ModelComponent`、`ParticleComponent` 等。

2. **一帧的渲染与提交：**
   此阶段在 PICO 空间引擎进程中发生。引擎在每帧开始时，会获取所有空间应用提交的渲染任务，经过统一渲染与合成，生成每一帧的最终图像并提交给合成器。该阶段可进一步分为两个子阶段：
   * **CPU 组织和提交绘制命令**：CPU 接收各应用提交的渲染任务后，将其整理成 GPU 能执行的绘制命令列表（即 “一帧要画哪些东西的清单”），并准备好渲染所需的资源（即 “这一帧绘制所需的所有材料”），然后将任务列表提交至 GPU。
   * **GPU 根据绘制命令完成渲染**：虽然 CPU 与 GPU 异步工作，但 GPU 需要在收集完当前帧所有的绘制命令后，才开始执行这一帧的最终渲染。因此，若 CPU 组织命令耗时过长，会导致 GPU 空转等待；反之，若 GPU 负载过重，也会阻塞下一帧的 CPU 提交。GPU 完成渲染后，会通过同步机制通知合成器，表示当前帧已可用。

3. **合成器获取这一帧：**
   合成器会在预期的时刻，尝试获取 PICO 空间引擎提交的最新帧。如果未能按时获取（例如，由于引擎处理超时），合成器会复用前一帧的画面进行显示。因此，为确保流畅的视觉体验（即应用的显示帧率与硬件刷新率保持一致），PICO 空间引擎必须在规定时间内完成每帧的提交。

4. **合成器完成内容的最终上屏显示：**
   图像帧抵达合成器后，还需经过图层合成、VR 畸变校正等一系列步骤，最终才会在正确的时间显示在屏幕上。这些步骤均由系统自动完成，无需额外关注。

## 常见瓶颈与定位
理想情况下，每个空间应用及 PICO 空间引擎都应满速运行。在 90Hz 刷新率的设备上，这意味着帧率（FPS）需稳定在 90。只有这样，才能确保每一帧画面都准时显示，保障优质体验。
如何避免系统优化策略对性能诊断的影响：

* **空间应用的帧率受限**：基于当前资源使用情况，在高负载时，系统会主动降低非焦点 WindowContainer 的帧率。因此，需确保当前调试中应用的 WindowContainer 处于焦点状态。
* **PICO 空间引擎的帧率受限**：当 HMD 几乎静止、无交互输入且无内容更新时，为降低功耗，PICO 空间引擎可能会进入低帧率模式。因此，建议在真机上调试应用时避免同时出现以上情况。

你可以通过 Perfetto Trace 获取应用进程及 PICO 空间引擎的帧率（详见《[获取并分析 Trace 记录](./spatial-sdk_性能与调试_获取并分析-trace-记录.md)》）。如果发现帧率不稳定或持续低于预期，就需要定位性能瓶颈。
基于当前统一渲染的帧同步机制，空间应用会等待 PICO 空间引擎消费完当前帧后才开始下一帧的处理，因此空间应用的帧率不会高于 PICO 空间引擎的帧率。大多数情况下，空间应用和 PICO 空间引擎的帧率应相等且均为 90 FPS，否则就说明出现了性能瓶颈，具体可以分为下文中的几种情况。
### 仅空间应用出现性能瓶颈

* **现象**：
   空间应用的帧率低于 90 FPS，但 PICO 空间引擎的帧率为 90 FPS（即满速运行）。
* **感知**：
   * 在 Shared Space 下，仅当前应用的内容卡顿，其余视觉元素（如其他应用、系统 UI）保持流畅。
   * 在 Full Space 下，由于该应用是唯一内容源，视野中的所有内容都可能卡顿。
* **分析**：
   这种情况的典型原因是应用自身的单帧处理耗时过长。以下图为例，第 N+1 帧执行超时，错过了 PICO 空间引擎的消费窗口，只能顺延至 PICO 空间引擎的 X+2 帧，而第 N+2 帧又必须等待第 N+1 帧被消费后才能开始，若此情况频繁发生，就会导致应用帧率下降，出现卡顿。

* **排查建议**：
   针对空间应用的性能瓶颈，可以参考《[性能优化](./spatial-sdk_性能与调试_性能优化.md)》中的 “问题排查” 部分，尝试定位具体的问题类型，并重点排查《[获取并分析 Trace 记录](./spatial-sdk_性能与调试_获取并分析-trace-记录.md)》中提到的与帧循环相关的 Trace。

### 仅 PICO 空间引擎出现性能瓶颈

* **现象**：
   空间应用与 PICO 空间引擎的帧率均低于 90 FPS，且两者的帧率相等。
* **感知**：
   无论在 Shared Space 还是 Full Space，视野中的所有内容（包括其他应用和系统 UI）都会出现卡顿。
* **分析**：
   这通常意味着 PICO 空间引擎遇到了瓶颈。为准确定位，建议在仅运行单个空间应用的情况下进行调试，以排除其他应用的干扰。瓶颈主要分为 CPU 和 GPU 两类。

**PICO 空间引擎的 CPU 瓶颈**

* **原因**：
   在统一渲染架构下，CPU 瓶颈通常是因为单帧内收到的渲染任务过多（例如，场景中绘制调用数量过大），导致准备绘制命令列表的耗时过长。
* **示例：**
   以下图为例，帧 N+1 在 CPU 阶段的执行时间过长，导致 GPU 在完成了帧 N 后，长时间收不到新的绘制命令队列，只能处于空闲状态。

* **排查建议**：
   参考《[场景复杂度](./spatial-sdk_性能与调试_场景复杂度与应用性能.md)》中的 “模型数量” 部分，并且重点排查《[获取并分析 Trace 记录](./spatial-sdk_性能与调试_获取并分析-trace-记录.md)》中提及的场景渲染相关 Trace。Trace 中展示了一段时间内 PICO 空间引擎中各类绘制命令的数量统计。

**PICO 空间引擎的 GPU 瓶颈**

* **原因**：
   GPU 瓶颈通常由过高的场景复杂度导致，例如模型过于复杂、三角面数过多、纹理尺寸过大、光源或阴影数量过多等，这些都会显著增加 GPU 渲染管线的执行时间。
* **示例**：
   以下图为例，帧 N 在 GPU 阶段的执行时间过长，导致帧 N+1 在 CPU 阶段需要等待帧 N 完成后才能进行绘制命令队列的提交，CPU 长时间处于阻塞状态。

   **排查建议**：
   参考《[场景复杂度](./spatial-sdk_性能与调试_场景复杂度与应用性能.md)》中的 “模型复杂度”、“三角面数量”、“纹理大小”、“光源和阴影数量” 等部分，并且重点排查《[获取并分析 Trace 记录](./spatial-sdk_性能与调试_获取并分析-trace-记录.md)》中提及的场景渲染相关 Trace。Trace 中展示了一段时间内 PICO 空间引擎中各类三角面的数量统计。

### 空间应用和 PICO 空间引擎均出现性能瓶颈

* **现象**：
   空间应用和 PICO 空间引擎的帧率均低于 90 FPS，且空间应用的帧率低于 PICO 空间引擎的帧率。这是上述两种情况的叠加，状况最为复杂。
* **感知**：
   无论在 Shared Space 还是 Full Space 下，视野中所有内容均出现明显卡顿。
* **排查建议**：
   1. 首先，在仅运行单个应用的状态下调试。
   2. 请参考上文 ”仅 PICO 空间引擎出现性能瓶颈“ 部分的排查建议，优先解决引擎的性能瓶颈，将其帧率优化至 90 FPS。
   3. 引擎性能达标后，再参考 “仅空间应用出现性能瓶颈” 部分的排查建议，优化你的空间应用性能。
